# F13. 행별 blame 보기 (R12)

관련: [F7 역사](F7-common.md) 2절, [F5 문서 화면](F5-page-view.md), [F8 마이그레이션](F8-migration.md), [02 데이터 모델](../02-data-model.md), 단계 [M7](../phases/M7-history-p1.md) (M4 직후 선행 구현)

문서 원문(마크다운) 각 줄을 마지막으로 바꾼 리비전·작성자·시각을 보여 준다 (`git blame`과 같은 개념).

## 1. 가능 여부 검토 (M4 이후 실데이터)

| 항목 | 값 | 판단 |
|------|----|------|
| 리비전 저장 방식 | 버전마다 본문 전체 저장 (`page_revisions.content`) | 재구성 없이 줄 diff만 하면 됨 → 가능 |
| 이전 이력 | Wiki.js 이력 1,609건 + 현재 168건. 각 리비전에 당시 작성자·시각 보존 | 이전 전 이력까지 blame 가능 |
| 문서당 리비전 | 평균 9.3, 최대 295 (`nems/프로젝트/KT_INMSGGW`, 본문 합계 12MB) | 조회마다 전체 계산은 느림 |
| 최악 문서 전체 계산 | Python difflib 3.0초 (참고치) | 캐시 + 증분 계산 필요 |

결론: 가능. 계산 결과를 문서별로 캐시하고, 새 리비전이 생기면 캐시된 버전 이후 리비전만 이어서 계산한다.

## 2. 계산 방식

1. 리비전을 버전 오름차순으로 순회하며 직전 버전과 줄 단위 diff (Myers, java-diff-utils)
2. 변경 없는 줄은 이전 귀속(버전)을 유지, 추가·변경된 줄은 현재 버전으로 귀속
3. 결과는 `page_blame(page_id, version, lines)`에 저장. `lines`는 줄별 귀속 버전의 런렝스 표현 (`버전*줄수,버전*줄수,…`)
4. 조회 시 캐시 버전 = 문서 버전이면 그대로, 작으면 그 이후 리비전만 적용해 갱신
5. 줄 구분은 `\n`. 한 줄짜리 긴 문단은 문단 전체가 한 줄로 귀속된다 (마크다운 원문 기준)

## 3. 화면

| 요소 | 사양 | 우선순위 |
|------|------|---------|
| 진입 | 문서 화면 상단 "행별 이력" 버튼 → `/blame/{path}` | P0 |
| 표시 | 원문 줄 번호 + 줄 내용(고정폭). 같은 리비전이 연속된 줄 묶음의 첫 줄에 `v버전 · 작성자 · 날짜` | P0 |
| 나이 색 | 오래된 변경은 옅게, 최근 변경은 진하게 (왼쪽 띠) | P0 |
| 출처 구분 | 이전(Wiki.js) / 웹 / 에이전트 / 시스템 배지 | P0 |
| 리비전 정보 | 묶음에 마우스를 올리면 편집 요약·시각 전체 표시 | P0 |
| 줄바꿈 토글 | 긴 줄 줄바꿈 켜기/끄기 (코드블록 설정과 공유) | P0 |
| 해당 리비전 보기·diff | 묶음 클릭 시 그 리비전 내용과 직전 대비 diff (역사 화면 F7 2절과 연결) | P1 (M7 역사 화면과 함께) |
| 시스템 변경 무시 | 링크 자동 갱신(`source=system`)과 이전 시점 본문 변환을 투명 처리: 같은 크기 변경 묶음은 이전 귀속 유지 | P1 |
| 렌더 화면 블록별 표시 | 문서 화면에서 블록(문단·코드블록)별 마지막 변경 표시 | P2 |
| MCP `get_blame` | 섹션 범위 blame 반환 | P2 |

## 4. 알려진 한계

- 이전 시점 마지막 리비전에는 마이그레이션 본문 변환(첨부 URL, `<details>`→접힘 코드블록 등)이 포함되어, 변환된 줄은 그 문서의 마지막 Wiki.js 작성자로 표시된다 (P1 "시스템 변경 무시"로 완화)
- 줄 이동은 삭제+추가로 취급한다 (이동 추적 없음)

## 5. 데이터 모델

```sql
-- Flyway V3
CREATE TABLE page_blame (
  page_id INTEGER PRIMARY KEY REFERENCES pages(id) ON DELETE CASCADE,
  version INTEGER NOT NULL,     -- 이 blame이 반영한 마지막 리비전 버전
  lines   TEXT NOT NULL         -- 런렝스: "1*12,3*2,1*40" (버전*줄수)
);
```

- 캐시이므로 지워도 다시 계산된다. 리비전 복원·이동은 새 리비전이므로 증분 계산으로 반영

## 6. API

| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET | `/api/v1/pages/{id}/blame` | `{ version, content, hunks: [{ start, count, version }], revisions: { 버전: { author, createdAt, source, action, summary } } }` |

- 권한: 문서 조회와 동일 (역사 열람 권한)
- `content`를 함께 반환해 blame과 본문 버전이 어긋나지 않게 한다

## 7. 성능

| 조건 | 목표 |
|------|------|
| 캐시 적중 | API p95 100ms 이내 |
| 최초 계산 (최악 문서 295 리비전) | 2초 이내, 1회만 |
| 리비전 1개 추가 후 | 증분 계산 200ms 이내 |

실측(구현 후, 실데이터): 최악 문서(295 리비전) 최초 계산 215ms, 캐시 적중 3~9ms, 195문서 전체 최초 계산 합계 0.5초. java-diff-utils 4.18(Myers) 사용.

## 8. 완료 기준

| 항목 | 기준 |
|------|------|
| 귀속 | 3개 리비전에서 각각 바꾼 줄이 해당 버전·작성자로 표시 |
| 증분 | 캐시 생성 후 리비전 추가 시 전체 재계산 없이 갱신, 결과가 전체 재계산과 동일 |
| 이전 이력 | 이전 문서의 blame에 Wiki.js 시절 작성자·날짜 표시 |
| 성능 | 7절 기준 충족 |
